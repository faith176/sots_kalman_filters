\section{Implementation Overview}

\begin{figure}
    \centering

    \caption{UML class diagram.}
    \label{fig:uml-model}
\end{figure}

\figref{fig:uml-model} presents the UML class diagram of the implemented system.  At the center of the model is the \texttt{Event} class, which represents both observed and reconstructed events flowing through the system. Each event contains an identifier, event type, source identifier, event timestamp, value, status, and an associated confidence value.

Events are propagated via the \texttt{EventStream}, which acts as the primary communication backbone of the system. The event stream provides a publish--subscribe abstraction through which all event producers and consumers interact. This enables loose coupling and supporting a cross-language architecture in which Python- and Java-based components operate over the same logical event stream. The realization of the event stream is provided by the \texttt{Client} and \texttt{Server} classes, which together implement ZeroMQ-based message passing as the transport layer of the \texttt{EventStream}. The server is responsible solely for routing events, while the client is used internally by the event stream to manage partitions and connections.

External data producers are represented by the \texttt{EventSource} class. Each event source is contains a source identifier, event type, and expected reporting interval, and is responsible for generating observed events and publishing them to the event stream. Event sources implement the \texttt{EventGenerator} interface, allowing them to be treated uniformly as event producers.

Event supervision is handled by the \texttt{Coordinator}, which implements the \texttt{EventConsumer} interface. The coordinator monitors incoming events for each source, maintains an expected schedule, and detects when observations are missing. When an expected event fails to arrive within the configured tolerance window, the coordinator triggers reconstruction by notifying the corresponding \texttt{Reconstructor}.

Each \texttt{Reconstructor} is associated with a specific event source and implements the \texttt{EventGenerator} interface. Observed events are forwarded to the reconstructor to update its associated \texttt{Predictor}, while missing events cause the reconstructor to request an estimate and confidence for the expected event time. The reconstructor then synthesizes a reconstructed \texttt{Event}, and publishes it into the event stream. State estimation is done by the \texttt{Predictor}, which maintains an internal representation of system state for a given event source. In this thesis, predictors are realized using Kalman filters, which support recursive state estimation and explicitly track estimation uncertainty.

Event processing is realized by the \texttt{EventProcessor} and \texttt{EventPattern} classes. The class hierarchy distinguishes between atomic and composite pattern definitions, reflecting the structure used to construct higher-level events from lower-level detections.The event processor is implemented in Java using the Esper \cite{esper_reference}.



\section{Event Stream Infrastructure}
The event stream provides the primary mechanism for propagating events throughout the system. Events are serialized into a standardized JSON payload (Listing~\ref{lst:event-json}), enforcing a consistent schema across all event types and implementation languages. Reconstructed events are injected into the same event stream as observed events and require no special handling by downstream consumers, ensuring a uniform processing model throughout the pipeline.

\begin{lstlisting}[language=json, caption={Example standardized event payload}, label={lst:event-json}]
{
  "event_id": "e7c1b9f4-42b1-4d3b-a6a9-9f82d3f1c021",
  "source_id": "sensor_A",
  "event_type": "temperature",
  "timestamp": "2024-03-21T14:32:05.120Z",
  "confidence": 1,
  "value": 73.4,
  "metadata": {
    "reconstructed": false,
  }
}
\end{lstlisting}

A ZMQ server relays event messages by receiving published payloads from client components and forwarding them to subscribed clients.
Subscribed clients process incoming events through registered callback handlers.

The system uses ZMQ topic filtering to separate observed and reconstructed events at the messaging level (\tabref{tab:zmq-topics}). Observed events are published under topics of the form \texttt{observed.<source\_id>}, while reconstructed events are published under \texttt{reconstructed.<source\_id>}. Components subscribe selectively based on their responsibilities, allowing them to receive only the subset of events relevant to their function rather than parsing and discarding irrelevant events.

\section{State Estimation and Confidence Derivation}
\label{sec:predictor-confidence}
In the proposed architecture, predictors are responsible for maintaining an estimate of the system state associated with each event source and for producing state predictions when observations are missing. For the implementation presented in this thesis, a Kalman filter is selected as the predictor due to its recursive state estimation capabilities.

\paragraph{Kalman filter state estimation.}
Kalman filters provide a recursive method for estimating the state of a dynamical system based on a sequence of observations \cite{kalman1960filtering,bishop2001introduction}. The system state at time step $k$ is represented by a state vector $\vec{x}_k$, which describes the internal state of the system at that time. Uncertainty in the state estimate is represented by an associated covariance matrix $\Sigma_k$, which captures both the expected variance of individual state variables and correlations between them. State estimation proceeds iteratively through a prediction and update cycle.


\paragraph{Prediction step.}
In the prediction step, the filter propagates the previous state estimate forward in time using a system model. This model is represented by a state transition matrix $\mathbf{F}_k$, which describes how the system state evolves between time steps. In addition to the internal system dynamics, known external influences on the system, such as control actions or scheduled inputs, may be incorporated through an input vector $\vec{u}_k$ and an associated control matrix $\mathbf{B}_k$. Uncertainty arising from unmodeled dynamics and external disturbances is captured by the process noise covariance matrix $\mathbf{Q}_k$. The predicted state and covariance are given by
\[
\vec{x}_{k|k-1} = \mathbf{F}_k \vec{x}_{k-1} + \mathbf{B}_k \vec{u}_k,
\qquad
\Sigma_{k|k-1} = \mathbf{F}_k \Sigma_{k-1} \mathbf{F}_k^{T} + \mathbf{Q}_k.
\]

\paragraph{Update step.}
When a new measurement $\vec{z}_k$ becomes available, the update step refines the predicted state using this observation. The measurement model is defined by a matrix $\mathbf{H}_k$, which maps the system state to the measurement space, while measurement uncertainty is represented by the measurement noise covariance $\mathbf{R}_k$. The Kalman gain $\mathbf{K}_k$ determines how strongly the filter adjusts its prediction based on the measurement, balancing trust between the predicted state and the observed value:
\[
\mathbf{K}_k = \Sigma_{k|k-1} \mathbf{H}_k^{T}
\left( \mathbf{H}_k \Sigma_{k|k-1} \mathbf{H}_k^{T} + \mathbf{R}_k \right)^{-1}.
\]
Using the Kalman gain, the state estimate and covariance are updated as
\[
\vec{x}_k = \vec{x}_{k|k-1} + \mathbf{K}_k \left( \vec{z}_k - \mathbf{H}_k \vec{x}_{k|k-1} \right),
\qquad
\Sigma_k = \Sigma_{k|k-1} - \mathbf{K}_k \mathbf{H}_k \Sigma_{k|k-1}.
\]
This recursive structure allows the predictor to maintain a current estimate of the system state over time.

\subsubsection{Deriving Confidence from Normalized Innovation Squared}
Kalman filters rely on assumptions about system dynamics and measurement noise \cite{simon2006optimal}. Consistency tests are used to assess whether the filter’s behavior during operation remains aligned with these modeling assumptions \cite{gamse2014statistical}. Specifically, such tests evaluate whether the discrepancies between predicted and observed measurements are statistically plausible given the uncertainty represented by the filter. When a filter is inconsistent, its estimates may become overconfident or fail to reflect deviations between the model and the observed system behavior.

A range of consistency diagnostics for Kalman filters has been proposed in the literature. Residual-based tests examine measurement innovations, defined as the difference between an observed measurement and its predicted value produced by the filter. State domain tests assess whether estimation errors remain within bounds implied by the posterior covariance matrix. Structural indicators characterize properties of the underlying system and estimator, including observability (whether the system state can be inferred from available measurements), controllability (whether the system state can be influenced through inputs), and Kalman gain behavior \cite{bar2001estimation,gamse2014statistical,piche2016online, griebel2020kalman}. Together, these diagnostics characterize whether the uncertainty represented by the estimator remains consistent with observed system behavior during operation, as well as different aspects of model adequacy.

% follows a chi square distribution so its bounded

In this work, confidence values are derived from the normalized innovation squared (NIS). NIS is based on the measurement innovation, defined as the difference between an observed measurement and the corresponding value predicted by the filter. The innovation quantifies how much new information a measurement provides relative to the current state estimate.

For a measurement $\vec{z}_k$ at time step $k$, the innovation is given by $\vec{z}_k - \mathbf{H}_k \vec{x}_{k|k-1}$, where $\vec{x}_{k|k-1}$ represents the predicted state estimate and $\mathbf{H}_k$ is the measurement matrix. The expected uncertainty of this innovation is quantified by the innovation covariance $\mathbf{S}_k$, defined as
\[
\mathbf{S}_k = \mathbf{H}_k \Sigma_{k|k-1} \mathbf{H}_k^{T} + \mathbf{R}_k,
\]
where $\Sigma_{k|k-1}$ is the predicted state covariance and $\mathbf{R}_k$ represents measurement noise.

The NIS statistic is then defined as
\[
\mathrm{NIS}_k =
\left( \vec{z}_k - \mathbf{H}_k \vec{x}_{k|k-1} \right)^{T}
\mathbf{S}_k^{-1}
\left( \vec{z}_k - \mathbf{H}_k \vec{x}_{k|k-1} \right).
\]

In the proposed architecture, the normalized innovation squared (NIS) \cite{bar2001estimation} statistic serves as the basis for deriving confidence values associated with reconstructed events. Intuitively, NIS measures how surprising a measurement update is relative to what the filter predicts should be observed. Larger NIS values indicate lower consistency between the model and the observation, while smaller values indicate higher consistency. This interpretation is enabled by the fact that NIS follows a known statistical distribution (chi-square) determined by the measurement model, which allows NIS to be evaluated online as measurements arrive, either at individual time steps or over short time windows, to assess whether observed behavior remains consistent with the filter’s expectations. During periods in which measurements are unavailable, confidence follows a gradual decay that reflects increasing reliance on prediction as the estimator covariance grows. By mapping NIS values to confidence, reconstructed events are annotated with confidence values that reflect how well the underlying state estimate agrees with recent observations.



\section{Event Processing Implementation}\label{sec:event-processing}
Complex event processing is implemented using the Esper CEP engine \cite{esper_reference}. 
The implementation distinguishes between atomic and complex event patterns. Atomic patterns define assertions over sequences of events, and may incorporate confidence constraints to filter uncertain observations. Complex patterns compose previously detected patterns, enabling higher-level reasoning over sequences of events. Listing~\ref{lst:atomic-patterns} shows example atomic pattern definitions expressed in EPL.

\begin{lstlisting}[language=json, caption={Example atomic event pattern definitions}, label={lst:atomic-patterns}]
[
  {
    "name": "Overspeeding",
    "type": "atomic",
    "epl": "@Name('Overspeeding') select e from Event as e where e.src='speed-1' and e.value > 25 and confidence > 0.75"
  },
  {
    "name": "EngineOverheat",
    "type": "atomic",
    "epl": "@Name('EngineOverheat') select e from Event as e where e.src='engine-temp-1' and e.value > 25 and confidence > 0.75"
  }
]
\end{lstlisting}

Detected patterns, including both atomic and complex patterns, are re-injected into Esper as pattern records, allowing subsequent patterns to consume earlier detections. This enables a pattern-of-patterns processing model in which complex patterns are constructed incrementally from simpler ones. Listing~\ref{lst:complex-patterns} shows example complex pattern definitions, including specifications of how confidence is aggregated across events in a detected pattern.

\begin{lstlisting}[language=json, caption={Example complex event pattern definitions with confidence aggregation}, label={lst:complex-patterns}]
[
  {
    "name": "HighSpeedOverheat",
    "type": "complex",
    "epl": "@Name('HighSpeedOverheat') select a as over, b as heat from pattern [every a=PatternRecordStream(patternName='Overspeeding' and confidence > 0.75) -> b=PatternRecordStream(patternName='EngineOverheat' and confidence > 0.85)]",
    "confidence": { "aggregation": "avg" }
  }
]
\end{lstlisting}

Confidence aggregation is performed outside the CEP engine using simple strategies such as minimum, maximum, average, or latest confidence. For example, patterns detected on safety-critical services may require maximum confidence, fault-detection patterns may use minimum confidence to reflect worst-case uncertainty, and trend-based patterns may aggregate confidence using the average to smooth individual fluctuations. Confidence-aware assertions may be applied at both atomic and complex levels, enabling queries to reason explicitly about event occurrences while accounting for input uncertainty. Existing queries can be updated to require maximum confidence, restricting evaluation to observed events only and preserving backward compatibility with conventional CEP usage.
