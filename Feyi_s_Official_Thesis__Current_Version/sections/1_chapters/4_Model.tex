\chapter{Foundations of Event-Driven Processing under Missing Observations}\label{ch:model}

The literature review (\secref{sec:literature-review-key-takeaways}) identifies a reliability gap in SoTS: while system behaviour depends on continuous streams of events, existing approaches provide limited support for interpreting system behaviour when expected observations do not arrive. This gap is particularly evident in how event streams are processed during execution.

Event-driven processing derives higher-level system behaviour by detecting patterns over incoming events. When observations are missing or delayed, event-based reasoning may diverge from the system state it is intended to represent. Addressing this challenge therefore requires an explicit treatment of event-driven semantics under missing observations.

This chapter introduces an abstract model of event-driven operation that formalizes event generation, timing, and processing in the presence of missing observations. The model provides the foundation for the architectural requirements defined in this chapter and for the system architecture presented in \chref{ch:architecture}.


\section{Requirements}
\label{sec:requirements}
\input{tables/Architecture/requirements V4.tex}
At the computational level, reliability challenges in event-driven SoTS manifest as uncertainty in the data processed by CEP. Prior work has shown that missing events can undermine event-based reasoning and lead to inaccurate conclusions about system behaviour. Maintaining reliable operation under these conditions therefore requires explicit support for reasoning under uncertainty within the event processing pipeline.

In the CEP literature, \citet{wasserkrug2006taxonomy} classify different types of uncertainty, identifying missing data as a form of occurrence uncertainty originating at the event source. \citet{cugola2015complex} characterize uncertainty management as a fundamental requirement for CEP systems operating over real-world data, identifying three essential capabilities: the identification of uncertainty in input data, the explicit modeling of uncertainty, and the propagation of uncertainty from primitive to composite events.

Together, these results motivate a set of architectural requirements for event-driven systems that must operate in the presence of missing observations. The system must be able to identify, represent, and propagate uncertainty during event-driven computation. The resulting requirements are formalized in \tabref{tab:architecture-requirements}, grounding the proposed model in established CEP uncertainty theory while addressing the reliability gap identified for digital twins operating within SoTS (\secref{sec:literature-review-key-takeaways}).





\paragraph{Model Scope and Assumptions}
The model assumes that missing observations arise from finite, short-term interruptions rather than prolonged outages. This assumption constrains the applicability of the model to scenarios in which prediction-based inference is appropriate over limited time horizons. Accordingly, the prediction models used within the system are assumed to be capable of handling the expected duration of such interruptions and to provide uncertainty information over the corresponding prediction interval.
The treatment of late events is limited to classification. Retroactive correction of inferred results, reconciliation under delayed observations, and reordering across multiple event streams are outside the scope of this model and are left for future work (\chref{ch:conclusion}).


\section{Event Model and Stream Semantics}
\label{sec:events-streams}

An \emph{event} represents an observation about an underlying system or process being monitored and is defined as
\begin{equation}
e = \langle id, type, src, t, v, conf, m \rangle ,
\end{equation}
\noindent
where $id$ uniquely identifies the event, $type$ represents the class of the event, $src$ identifies the source of the event, $t$ is the event time indicating
when the observed phenomenon occurred, $v$ is the observed or inferred value, $conf \in \mathcal{C}$ is a confidence value associated with the event, and $m$ represents auxiliary metadata.

An \emph{event stream} $E$ is a sequence of events
\begin{equation}
E = \langle e_1, e_2, \dots \rangle .
\end{equation}

Events originate from a set of \emph{event sources} $\mathcal{S}$, which correspond to external systems or processes being observed and produce values $v$ as observations over time. Each event source $s \in \mathcal{S}$ is characterized by an identifier, an event type, and an expected sampling interval:
\begin{equation}
s = \langle id_s, type_s, \Delta_s \rangle .
\end{equation}
\noindent
The expected sampling interval $\Delta_s$ specifies the time between successive observations.

Event sources act as \emph{event generators} by formatting observations as events and publishing them to the event stream $E$. For each event $e$ originating from source $s$, the source attribute is set to $e.src = id_s$, and the type attribute is set to $e.type = type_s$. Observed events are assigned a maximal confidence value according to the confidence scale $\mathcal{C}$.
Events published to the stream are made available to downstream \emph{event consumers}, which observe and react to events in $E$.




\section{Handling Missing Events}
\label{sec:scheduling-missing}

According to \citet{wasserkrug2006taxonomy}, event streams are subject to occurrence uncertainty originating at their sources, such that observed event streams may represent only partial views of the underlying system behaviour. In event-driven systems, this uncertainty must be resolved at runtime to determine whether an expected observation has occurred or whether its absence should be interpreted as a delay or as missing.

Let $\kappa$ be an \emph{event consumer} that has access to the expected sampling intervals $\Delta_s$ of event sources $s \in \mathcal{S}$. Using the current system time $t_{\mathrm{now}}$, $\kappa$ compares expected observation times with the appearance of events in the event stream to classify the status of expected observations.

For each source $s \in \mathcal{S}$, let $t^{\mathrm{last}}_s$ represent the event time of the most recent event in $E$ originating from $s$ that has been accounted for by $\kappa$. The next expected observation time for source $s$ is defined as
\begin{equation}
t^{\mathrm{exp}}_s = t^{\mathrm{last}}_s + \Delta_s .
\end{equation}
A tolerance window $\varepsilon_s$ is associated with source $s$ and defines the acceptable deviation from the expected observation time.

Each expected observation is classified according to the set
\begin{equation}
\mathcal{O} = \{\textsc{Observed}, \textsc{Late}, \textsc{Missing}\}.
\end{equation}

An expected observation for source $s$ at time $t^{\mathrm{exp}}_s$ is classified as:
\begin{itemize}
    \item \textsc{Observed} if there exists an event $e \in E$ such that $e.src = id_s$, $e.type = type_s$, and $\lvert e.t - t^{\mathrm{exp}}_s \rvert \le \varepsilon_s$.
    \item \textsc{Late} if there exists an event $e \in E$ such that $e.src = id_s$, $e.type = type_s$, and $\lvert e.t - t^{\mathrm{exp}}_s \rvert > \varepsilon_s$.
    \item \textsc{Missing} if $t_{\mathrm{now}} > t^{\mathrm{exp}}_s + \varepsilon_s$ and no such event has been observed.
\end{itemize}
\noindent
Once an expected observation is classified as \textsc{Missing}, the model does not retroactively revise this classification upon later event arrival. Classification reflects the information available at the time of evaluation.




\section{Event Reconstruction and State-Based Inference}
\label{sec:state-based-inference}

For each event source $s \in \mathcal{S}$, let $r_s$ represent an \emph{event reconstruction mechanism} that acts as both an \emph{event consumer} and an \emph{event generator}. The behaviour of $r_s$ is governed by the classification of expected observations determined in \secref{sec:scheduling-missing}.
Each reconstructor $r_s$ contains a predictor with internal state $x_s$. As an event consumer, $r_s$ processes observed events associated with source $s$ in order to update this predictor state. As an event generator, $r_s$ emits reconstructed events corresponding to expected observations that are classified as missing.

The predictor supports two operations:
\begin{align}
\mathcal{U}_s\bigl(x_s^{i-1}, v_s^{i}\bigr)
&\quad\text{(update)}, \\
\hat{v}_s^{i} = \mathcal{P}_s\bigl(x_s^{i-1}\bigr)
&\quad\text{(prediction)}.
\end{align}

Each index $i$ corresponds to a successive expected observation for source $s$. When the expected observation is classified as \textsc{Observed}, the update operation $\mathcal{U}_s$ is applied, advancing the predictor state using the observed value $v_s^{i}$. When the expected observation is classified as \textsc{Missing}, the prediction operation $\mathcal{P}_s$ is applied, producing an estimated value $\hat{v}_s^{i}$ in the absence of an observation. Exactly one operation is applied at each step.

Uncertainty associated with inference is represented through a confidence value derived from the predictor state. A confidence function is defined as
\begin{equation}
conf_s^{i} = \mathcal{C}\bigl(x_s^{i}\bigr),
\end{equation}
\noindent
where confidence reflects the uncertainty accumulated by the predictor when operating without direct observation.

\section{Stream Augmentation}
\label{sec:confidence-stream-augmentation}

When an expected observation associated with source $s \in \mathcal{S}$ is classified as \textsc{Missing}, the reconstructor produces a replacement event defined as
\begin{equation}
\hat{e}_s^{i} =
\langle id, type_s, id_s, t^{\mathrm{exp}}_s, \hat{v}_s^{i}, conf_s^{i}, m_{\mathrm{pred}} \rangle ,
\end{equation}
\noindent
where $\hat{v}_s^{i}$ is the inferred value produced by the predictor, $conf_s^{i}$ is the associated confidence value derived from the predictor state, and $m_{\mathrm{pred}}$ records metadata indicating that the event was reconstructed rather than directly observed.

Reconstructed events are emitted into the event stream in the same manner as observed events. Observed and reconstructed events share a common structural representation, enabling uniform processing by downstream \emph{event consumers} and the incorporation of confidence-based queries.

The event stream is then extended to an augmented stream
\begin{equation}
E^{+} = E \cup \{ \hat{e}_s^{i} \},
\end{equation}

\section{Confidence-Aware Event Processing}
\label{sec:confidence-aware-semantics}

The augmented event stream $E^{+}$ produced by the model is intended to be consumed by downstream event driven processing components. An \emph{event processor} is modeled as an \emph{event consumer} that observes events from $E^{+}$ and evaluates event patterns and temporal relations over the stream.

Let $e \in E^{+}$ be an event with an associated confidence value $conf(e) \in \mathcal{C}$. Event patterns and temporal relations may incorporate confidence values through additional predicates or aggregation functions, allowing processing logic to regulate pattern evaluation based on the confidence associated with inferred events.

At a basic level, confidence-aware processing may require individual events to satisfy a threshold condition
\begin{equation}
conf(e) \ge \theta ,
\end{equation}
\noindent
where $\theta$ is an application-defined confidence threshold. Such conditions allow event processors to suppress low-confidence events or to rank candidate matches according to their associated confidence values.

More complex patterns may combine the confidence of multiple events. Consider, for example, a temporal pattern requiring an event of type $A$ to be followed by an event of type $B$ within a time window $\tau$. Let $e_A$ and $e_B$ denote the corresponding events, with associated confidence values $conf(e_A)$ and $conf(e_B)$. The confidence of the composite pattern may be approximated by an aggregation function, for example
\begin{equation}
conf(A \rightarrow B) = conf(e_A) \cdot conf(e_B).
\end{equation}
Alternative aggregation strategies may also be used, including minimum, maximum, average, or recency-based confidence, depending on application requirements.

These mechanisms enable uncertainty introduced by reconstructed events to be accounted for explicitly during pattern evaluation, while preserving the structural and temporal semantics of event driven processing. In particular, confidence-aware processing supports threshold-based triggering, prioritization, and ranking of detected event patterns without requiring changes to the underlying event processing model.

\section{Reliability through Continuity and Correctness in Event Processing}\label{sec:reliability-implications}
% Reliability Enabled by Continuity and Correctness in Event Processing
Event-driven systems operating in open environments are subject to disruptions at their data sources. \citet{wasserkrug2006taxonomy} define a taxonomy of uncertainty in CEP systems, including occurrence uncertainty arising when expected events fail to appear in the event stream. In traditional CEP systems, the absence of expected observations is not explicitly represented, resulting in incomplete event streams that can compromise higher-level reasoning.

Missing observations arise when expected observations from event sources fail to enter the event stream. Reliability, as defined by \citet{avizienis2004basic}, is the ability of a system to continuously deliver correct service. In event-driven systems, this continuity depends on maintaining an up-to-date representation of the observed process through the event stream. Traditional CEP engines advance computation only when new events arrive. When expected events do not appear, gaps arise in the stream and event histories become incomplete or inconsistent. As a result, detected patterns and derived results may drift from the system behaviour they are intended to represent, undermining reliable service delivery.

Existing uncertainty-aware CEP frameworks primarily address uncertainty in arriving events, including noisy attribute values, uncertain timestamps, and rule-level ambiguity, while continuing to assume uninterrupted event flows \citep{alevizos2017probabilistic}. Probabilistic approaches based on Bayesian networks, interval-based temporal reasoning, and lineage- or NFA-based models require the arrival of input events to trigger computation and therefore cannot represent or reason about missing observations \citep{wasserkrug2010efficient, wasserkrug2012model, zhang2013recognizing, shen2008probabilistic, kawashima2010complex, chuanfei2010complex, wang2013complex}. Similarly, uncertainty-aware extensions to existing CEP engines enrich reasoning over partially observed events, but remain inactive when the event stream temporarily disappears \citep{cugola2015introducing, moreno2019managing}.

The model proposed in this chapter addresses this limitation by explicitly detecting when expected events fail to arrive and responding to these absences through event reconstruction. Reconstructed events provide a representation of missing observations within the event stream, reducing the impact of gaps on event-driven processing and supporting continuity of operation. Confidence values derived from the predictor are explicitly attached to reconstructed events. This enables event processors to assess how reconstructed observations affect the correctness of detected patterns and to evaluate pattern results using confidence-based predicates or thresholds.
