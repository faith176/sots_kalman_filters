\chapter{Results}\label{ch:results}
This chapter presents the experimental evaluation of the proposed architecture. Building on the architectural design detailed in Chapter~\ref{ch:architecture}, this chapter quantitatively assesses the system’s ability to maintain event reasoning continuity and correctness when constituent systems intermittently fail or rejoin the SoTS.  

The chapter is organized in two main parts. The first part (\secref{sec:results-eval}) introduces the evaluation scenario, outlining the problem formulation, baseline configurations, simulation environment, and quantitative metrics used to assess performance. The second part (\secref{sec:results-res}) presents and analyzes the experimental findings, comparing the proposed architecture against baseline configurations.


\section{Evaluation}\label{sec:results-eval}
The following section defines the evaluation scenario used to examine how the proposed architecture sustains dependable event reasoning when constituents intermittently fail or rejoin the SoTS.

\subsection{Problem Formulation}
\label{subsec:results-eval-problem-formulation}

The evaluation aims to quantify the extent to which the proposed reliability-enhanced Complex Event Processing (CEP) architecture sustains dependable event reasoning in a dynamic System of Twinned Systems (SoTS) environment subject to transient disruptions.

Let the SoTS be represented as a set of constituent systems 
$\mathcal{C} = \{ c_1, c_2, \dots, c_n \}$ 
that generate event streams 
$\mathcal{E} = \{ e_1, e_2, \dots, e_m \}$ 
corresponding to sensor observations, reconstructed values, or detected complex events.
Each constituent $c_i$ may temporarily leave or rejoin the system, causing partial loss of observable data.

\smallskip
At each discrete time step $t$, the system receives a set of observed events 
$\mathcal{E}_t^{obs} \subseteq \mathcal{E}$ 
originating from the currently active constituents in the SoTS.  
These observations are forwarded to the reconstruction module $\mathcal{R}(\cdot)$, which passes through all observed events unchanged while estimating missing events that would have been produced by inactive constituents expected to emit data at that time:
\begin{equation}
    \mathcal{E}_t^{rec} = \mathcal{R}(\mathcal{E}_{1:t}^{obs}).
\end{equation}

The CEP engine $\Phi(\cdot)$ continuously evaluates event patterns over this input stream to infer higher-level complex events:
\begin{equation}
    \hat{p}_t = \Phi(\mathcal{E}_{1:t}^{rec}),
\end{equation}
where $\hat{p}_t$ denotes the predicted occurrence of pattern $p$ at time $t$.

\smallskip
The reliability objective is to maintain both \textit{continuity} and \textit{correctness} of these pattern detections during transient disruptions.  
Hence, for each evaluation run, we define two outcome sets:
\begin{itemize}[noitemsep, topsep=0pt]
    \item $\mathcal{P}^{true}$ — the ground-truth pattern occurrences computed from complete, fault-free data;
    \item $\mathcal{P}^{det}$ — the detected patterns produced by the CEP under injected fault scenarios.
\end{itemize}


The evaluation problem can be expressed as:
\begin{quote}
\textit{Given a dynamic SoTS where constituent systems may temporarily fail or rejoin, evaluate whether the proposed architecture can preserve event reasoning correctness and continuity better than a baseline CEP system, under controlled fault injection.}
\end{quote}

\subsection{Baseline Configurations}
\label{subsec:results-eval-baselines}

To contextualize the results of the proposed architecture, we compare it against a set of baseline configurations that differ in how they handle missing events caused by transient constituent unavailability. All configurations use the same CEP runtime (Esper) and identical event pattern definitions, ensuring that differences in performance arise solely from how missing data is treated prior to event reasoning.

\paragraph{B0: CEP without reconstruction.}
In this baseline, the CEP engine processes only the observed events produced by currently active constituents. 
Events originating from inactive constituents are absent and no reconstruction is attempted. 
This represents the default CEP behavior and establishes a lower bound for reasoning continuity.
Since no estimates are generated, confidence values are undefined, and confidence-based metrics are reported as not applicable.

\paragraph{B1: CEP with simple imputation.}
This configuration forwards observed events as-is and fills gaps caused by inactive constituents using a simple statistical heuristic (e.g., last-observation-carried-forward or local mean). 
To maintain comparability across metrics, a surrogate confidence value is synthesized for each reconstructed event based on the time elapsed since the last true observation:
\[
c_t = \exp(-\lambda \, g_t),
\]
where $g_t$ is the number of consecutive missing intervals and $\lambda$ controls the rate of confidence decay. 
This heuristic confidence provides a coarse approximation of increasing uncertainty over longer data gaps.

\paragraph{B2: CEP confidence-aware reconstruction (proposed).}
In the proposed architecture, all observed events are passed through unchanged, while missing events expected at each time step are reconstructed using the reliability-enhanced module $\mathcal{R}(\cdot)$. 
This module integrates estimator-specific models (e.g., Kalman or Particle Filters) to infer missing values and produces an associated confidence score derived from the estimator’s internal uncertainty.

\paragraph{B3: Oracle CEP.}
To establish an upper bound on achievable performance, we include an oracle configuration in which the CEP engine receives the complete, fault-free event stream that would be available if all constituents remained continuously active. 
No reconstruction or imputation is required, and all events are provided with perfect timeliness and correctness. 


\subsection{Simulation Environment}\label{subsec:results-eval-simulation-env}
To evaluate the architecture under controlled and repeatable conditions, the experiments use the Simulation of Urban Mobility (SUMO) framework~\cite{krajzewicz2012recent}. SUMO provides a traffic simulation environment that allows modeling of multiple road intersections and vehicle flows. 

Each intersection is represented as a constituent system within the SoTS, equipped with a virtual sensor that publishes event data such as vehicle counts and average speeds. To emulate the dynamic composition of a SoTS, selected sensors are programmatically deactivated and later reactivated during runtime, producing transient data gaps that reflect constituent departures and rejoinings.
