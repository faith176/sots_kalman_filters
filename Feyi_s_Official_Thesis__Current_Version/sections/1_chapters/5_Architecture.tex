\chapter{System Architecture}\label{ch:architecture}
This chapter presents the architecture of the event processing system proposed in \chref{ch:model} to support reliable operation. The architecture defines the system’s structural organization, the responsibilities of its components, and the flow of events under both normal operation and conditions involving missing observations.

\section{Architectural Overview}
\label{sec:architecture-overview}
At a high level, the system is organized around the processing of events originating from external sources. These events are propagated through an event stream, where their arrival is monitored to determine whether they should be forwarded directly for processing or reconstructed when expected observations are missing. Reconstructed events carry the confidence of the estimates, allowing this information to be taken into account during event processing. \figref{fig:domain-model} presents the domain model of the architecture, showing the key conceptual entities and their relationships.

\begin{figure}[t]
\centering
\includegraphics[width=\linewidth]{figures/Architecture/Domain Model.drawio.pdf}
\caption{Domain model.}
\label{fig:domain-model}
\end{figure}

An \emph{Event} represents an observation produced by an event source. Events are propagated using an \emph{Event Stream}, which provides a sequence of events to downstream elements of the system. \emph{Event sources} generate observations at specific intervals but are assumed to be flawed, allowing events to be absent.
To support reliable operation under such conditions, the architecture introduces explicit coordination and estimation elements. A \emph{Coordinator} monitors the arrival of events from each source and determines whether events arrive on time or are missing. When an expected event is absent from the \emph{Event Stream}, a \emph{Reconstructor} uses a \emph{Predictor} to synthesize a replacement event. An \emph{Event Processor} consumes both observed and reconstructed events to evaluate \emph{Event Patterns}. 
Event patterns represent higher-level abstractions over streams of events. An \emph{Atomic Event Pattern} captures a basic behavioural condition over one or more events. A \emph{Complex Event Pattern} represents a composition of atomic and complex event patterns, enabling the detection of higher-level situations formed by multiple correlated behaviours occurring.


\section{Component Architecture and Responsibilities}
\label{sec:architecture-components}

\figref{fig:component-model} presents the component model of the system, illustrating the major architectural elements and the interfaces through which they interact. This design enables components to interact through well-defined interfaces while remaining loosely coupled. The responsibilities of each component are described below.

\begin{figure}[t]
\centering
\includegraphics[width=\textwidth]{figures/Architecture/High Level Component Diagram.drawio.pdf}
\caption{Component model.}
\label{fig:component-model}
\end{figure}

\paragraph{Event Source}
An event source represents an external system, sensor, or data generator that produces observations of a monitored process. Its responsibility is to generate observations and encapsulate them as events that conform to the system’s event schema. These observed events are emitted into the event stream for downstream processing.

\paragraph{Event Stream}
The event stream provides a transport and routing abstraction for all events in the system. It acts as a shared event bus through which observed and reconstructed events are delivered to coordination and processing components.

\paragraph{Coordinator}
The coordinator is responsible for monitoring the arrival of observed events and reasoning about their expected timing. For each event source, it maintains an expected schedule derived from configuration parameters such as reporting interval and tolerance. Based on this schedule, the coordinator identifies missing observations and initiates reconstruction when expected events do not arrive within the configured time window.

\paragraph{Reconstructor}
Each event source is associated with a reconstructor that manages reconstruction for that source. The reconstructor forwards observed events to its associated predictor for state update and performs reconstruction when notified of missing observations. For a missing event, it obtains an estimated value and associated confidence from its predictor, constructs a reconstructed event, and emits it into the event stream.

\paragraph{Predictor}
A predictor maintains an internal representation of the system state associated with a specific event source. It supports state updates using observed values and state prediction to produce estimates when observations are missing. Predictors also provide uncertainty measures associated with their estimates.

\paragraph{Event Processor}
The event processor evaluates atomic and complex event patterns over the event stream. It consumes both observed and reconstructed events and applies pattern definitions to detect higher-level events. Confidence associated with events may be incorporated into pattern evaluations. This allows pattern detection to account for uncertainty introduced by reconstructed observations.


\section{Event Processing and Reconstruction Flow}
\label{sec:architecture-sequence}

To illustrate the behaviour of the system, \figref{fig:sequence-model} presents the sequence model for event processing and reconstruction.

\begin{figure}[t]
\centering
\includegraphics[width=\textwidth]{figures/Architecture/Sequence Diagram.png}
\caption{Sequence model.}
\label{fig:sequence-model}
\end{figure}

\paragraph{Normal Observation Flow}
When an observation is produced by an event source, it is encapsulated as an event and emitted to the event stream. The coordinator assesses whether the event arrives within its expected temporal window. If so, the event is consumed by the reconstructor, which forwards the observed value to its associated predictor for state update. In parallel, the event processor evaluates relevant event patterns over the event stream.

\paragraph{Missing Observation Flow}
If an expected event does not arrive within the expected time, the coordinator detects the absence and requests reconstruction. The reconstructor queries the predictor to obtain an estimated value and confidence for the expected time and emits a reconstructed event.

\section{Mapping the Framework to the ISO~23247 Reference Architecture}\label{sec:dt-positioning}
As identified in the literature review (\secref{subsec:literature-review-results-standards}), standards adoption in SoTS remains fragmented and is largely limited to communication- and data-level concerns. To position the proposed SoTS framework within an established reference architecture, it is mapped to ISO~23247. This mapping relates the framework’s components to standardized architectural and functional entities (FEs) and shows how both observed and inferred event information can be integrated to support reliable digital twin operation within SoTS under imperfect data conditions.

\begin{figure}[t]
\centering
\includegraphics[width=\textwidth]{figures/Architecture/ISO 23247.drawio.pdf}
\caption{Positioning of the proposed framework within the ISO~23247 reference architecture.}
\label{fig:iso23247-mapping}
\end{figure}

\subsection*{Mapping to ISO~23247 entities}

ISO~23247 defines a domain- and entity-based reference architecture separating observable manufacturing elements (OMEs), device communication, digital twin, user, and cross-system concerns. The proposed framework spans these entities, with core functionality concentrated in the digital twin entity and supporting capabilities realized through the device communication and cross-system entities.

Observable manufacturing elements reside in the OME entity and represent the physical assets being monitored. According to ISO~23247, observations of OMEs are acquired through the data collecting functional entity. In the proposed framework, this functionality is realized within the device communication entity by an event source component, which interfaces with physical devices and produces raw observations as discrete events.

ISO~23247 defines the data translation functional entity for transforming collected data into standardized representations. This functionality is instantiated in the cross-system entity by a serialization component, which converts observations into a standardized event representation that can be exchanged across systems and components.

Within the digital twin entity, ISO~23247 defines the digital representation functional entity as an abstraction of OME state and behaviour. In the proposed framework, this digital representation is maintained as a standardized event stream, which serves as the primary interface through which synchronization, simulation, and analytic services interact.

Synchronization functionality, which ISO~23247 associates with maintaining consistency between the physical and digital representations, is handled by the coordinator and reconstructor components. These components extend the synchronization functional entity by explicitly accounting for the absence of expected events. The coordinator supervises event timing and detects violations of expected behaviour, while the reconstructor generates inferred events when observations fail to arrive within their expected windows and injects them back into the event stream. 
The predictor component instantiates the simulation functional entity defined in ISO~23247 to predict the behaviour of OMEs. The predictor updates its internal model in response to observed events and estimates the system state.

Finally, ISO~23247 assigns higher-level reasoning over digital twin data to the analytic service functional entity. This functionality is realized by the event processor component, which detects higher-level behaviour in event stream sequences and reasons over both observed and reconstructed events.
