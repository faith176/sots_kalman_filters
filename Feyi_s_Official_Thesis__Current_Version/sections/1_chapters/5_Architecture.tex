This chapter presents the architecture of the proposed framework designed to manage uncertainty in SoTS through real-time data reconstruction, confidence propagation, and event reasoning.

\subsection{Architectural Objectives}

The framework architecture is guided by two primary objectives that ensure reliable, interpretable, and interoperable operation across distributed SoTS constituents:

\begin{itemize}
    \item \textbf{Data Continuity:} Preserve uninterrupted information flow within the SoTS by detecting and reconstructing missing data, ensuring that downstream reasoning operates on complete event streams.  

   \item \textbf{Uncertainty Transparency:} Explicitly encode the reliability of reconstructed information as confidence values attached to each event, ensuring consistent handling of uncertainty throughout the processing pipeline.
\end{itemize}


% -------------------------------------------------------------
\subsubsection{Design Principles}
\label{sec:design_principles}

We follow these guiding principles to meet the architectural objectives defined: 

\begin{itemize}
    \item \textbf{Continuity under data loss:} Reconstruct missing events to maintain uninterrupted information flow
    \item \textbf{Transparency of uncertainty:} Represent reconstruction reliability explicitly through a \texttt{confidence} attribute attached to each event, allowing uncertainty to remain visible.
    \item \textbf{Loose coupling and modularity:} Use a publish–subscribe communication model to decouple data producers and consumers, enabling independent operation and flexible integration.
    \item \textbf{Separation of concerns:} Clearly differentiate the roles of data generation, reconstruction, coordination, and event detection to improve maintainability and extensibility.
    \item \textbf{Scalability and reusability:} Integrate heterogeneous components, streams, predictors, messaging clients, and CEP adapters, through a uniform interface and pluggable configuration design.

\end{itemize}.

These objectives address a core limitation of existing SoTS and CEP infrastructures, which often assume complete data streams. By integrating reconstruction and confidence tracking directly into the shared event pipeline, the framework replaces absence with approximation. Allowing information to remain accessible even under uncertainty.

\section{Overview}

The proposed framework adopts a layered, message-driven architecture that enables both autonomy and cooperation among DT constituents within a SoTS. Each DT operates as an independent node capable of reconstructing sensor data, propagating confidence, and performing local event reasoning while remaining connected to a shared asynchronous communication layer.

As shown in Figure~\ref{fig:ch4_context_diagram}, the framework follows a publish subscribe model: each DT publishes data from its own sensors to a shared event stream and may subscribe selectively to datastreams from other constituents. This preserves data ownership while allowing situational awareness to emerge through controlled information exchange. Each DT hosts a local instance of the SoTS framework, configured by a researcher to define subscriptions, reconstruction parameters, and complex event patterns. Through this mechanism, DTs can collaborate and access system-level information without relying on centralized coordination.

Figure~\ref{fig:ch4_container_diagram} presents the high-level architecture of the proposed framework. 
The system is organized into two primary layers: the Event Stream Layer, which provides the messaging infrastructure for asynchronous data exchange, and the Processing Layer, which hosts the active modules responsible for coordination, reconstruction, and reasoning. Solid arrows indicate event data flow, while dashed lines represent control signals.

At a high level, the framework operates as a continuous event pipeline that transforms incomplete sensor data into a reconstructed, uncertainty-aware stream. 
\textbf{Streams} act as data generators, emitting observed events that may contain temporal gaps due to missing readings. 
The \textbf{Coordinator} manages event scheduling and serves as the control point for dissemination, publishing available sensor readings to the observed stream or invoking the \textbf{Reconstructor} when expected events are absent. 
The \textit{Reconstructor} consumes all observed data and appends confidence metadata to each event.
It continuously updates the underlying predictors and generates synthetic events when required, producing a unified stream that merges both observed and reconstructed data.
The resulting reconstructed stream provides a temporally complete, confidence-annotated data flow for downstream reasoning by the \textbf{CEP Engine}. 
This design ensures that every event follows a consistent lifecycle from generation to interpretation, maintaining continuity and traceability across the entire pipeline.

\begin{enumerate}
    \item \textbf{Streams} generate sensor data and forward them to the Coordinator.  
    \item The \textbf{Coordinator} schedules event publication, detects missing readings, and triggers reconstruction when gaps are found.  
    \item The \textbf{Reconstructor} consumes observed events, appends confidence information, and imputes missing values when invoked.  
    \item All processed events are published to the \textit{reconstructed stream}, forming a continuous, confidence-annotated data flow.  
    \item The \textbf{CEP Engine} consumes the reconstructed stream for local or global pattern detection.  
\end{enumerate}

\section{Framework Architecture}
\label{sec:framework_architecture}

The framework is organized into three primary functional layers: Coordination, Reconstruction, and CEP; supported by a Messaging Layer.


\subsection{Coordination Layer}
\label{subsec:coordinator_layer}

The Coordination layer governs the scheduling and synchronization of data collection across multiple event streams.  Each stream corresponds to an initialized data source, which may be simulated, randomly generated, or connected to live sensor inputs. 

\paragraph{Core Function.}
The Coordinator advances according to a fixed tick-based schedule that defines the expected arrival time of events. 
At every tick, it polls the associated stream for a new reading. 
If a measurement is received within the allowed interval, it is published as an observed event. 
If no data are received before the timeout, the Coordinator detects a missing observation and issues a reconstruction request to the Reconstructor. 
Once the reconstructed event is produced, it is reintegrated into the reconstructed stream, ensuring that the resulting output remains temporally complete and consistent. 
Through this mechanism, the Coordinator provides time alignment, while handling dropped or delayed sensor updates.

\subsection{Reconstruction Layer}
\label{subsec:reconstruction_layer}

The Reconstruction layer preserves data continuity through statistical estimation. 
Its primary role is to infer missing sensor readings and quantify the reliability of each estimate. 
Each Digital Twin hosts its own Reconstructor instance, which maintains a continuously updated predictor that models local sensor dynamics.

\paragraph{Core Function.}
When the Coordinator detects a missing event, it invokes the Reconstructor to estimate the absent reading. 
The predictor is model-agnostic, any statistical or machine learning technique can be employed, but in practice, a \textit{Kalman filter} is used as the default estimator due to its recursive structure and built-in uncertainty propagation. 
The filter maintains a local state model of the sensor process:
\[
x_{t} = A x_{t-1} + B u_{t} + w_t, 
\qquad 
z_t = H x_t + v_t
\]
where \(w_t\) and \(v_t\) denote process and measurement noise, respectively. 
For each reconstruction, the filter outputs both an estimated state \(\hat{x}_t\) and an associated confidence score \(c_t \in [0,1]\), derived directly from the posterior covariance or normalized residuals.

Each reconstructed event is emitted in the form:
\[
\langle id,\, t,\, \hat{x},\, c,\, s=\text{reconstructed} \rangle
\]
and published to the \texttt{reconstructed} stream, ensuring that the output stream remains temporally complete and uncertainty-aware for subsequent processing.


\paragraph{Design Rationale.}
Kalman filters provide adaptive, noise-tolerant estimation well suited to continuous, partially observed data streams. 
Because covariance is an intrinsic part of the filter’s update mechanism, confidence values are obtained directly rather than computed through an external calibration process. 
This design supports model transparency and allows downstream components—such as the CEP Engine—to reason over reconstructed data using confidence as a compact representation of uncertainty.

\subsection{Complex Event Processing (CEP) Layer}
\label{subsec:cep_layer}

The \textit{Complex Event Processing (CEP)} layer performs higher-level reasoning over the unified event stream. 
It evaluates temporal patterns, correlation rules, and aggregation functions to derive composite events that represent system-level behaviors or anomalies. 
The layer is implemented using the Esper engine and interfaces with the messaging system through a lightweight Python adapter.

\paragraph{Core Function.}
Observed and reconstructed events are serialized in JSON format and streamed into the CEP engine, where event queries are defined using Esper’s Event Processing Language (EPL). 
These queries specify conditions and temporal windows for event detection, for example:
\begin{verbatim}
SELECT AVG(value) AS avgTemp
FROM TemperatureStream[range 10 sec]
WHERE confidence > 0.7;
\end{verbatim}
Each incoming event carries a confidence value that quantifies the reliability of its measurement or reconstruction. 
These confidence attributes are preserved throughout rule evaluation and can be aggregated or filtered based on user-defined policies.
As a result, the CEP layer produces complex events annotated with interpretable confidence levels, enabling uncertainty-aware reasoning and reliable downstream analytics.

\section{Messaging System}

\label{sec:messaging_modularity}

At the core of the framework lies an abstracted event-streaming channel that enables all events to exist within a shared communication space before being consumed by other layers. While the current implementation uses ZeroMQ~\cite{zeromq_org}, the design remains transport-agnostic and compatible with other publish–subscribe middleware supporting topic-based routing, such as MQTT~\cite{mqttspec}. This abstraction allows the messaging layer to serve as a reusable communication stream across deployments and enables constituent systems to interact through a unified event interface.

\paragraph{Common Event Plane and Topic Structure.}
All constituents communicate through a shared event plane—a logical message bus that captures the full lifecycle of events across the SoTS.
Messages are partitioned by event type using a simple yet expressive topic hierarchy:
The framework distinguishes between two primary event topics:
The framework maintains two primary event topics:
\begin{itemize}
    \item \texttt{observed.<stream\_id>} — original sensor readings as emitted from the physical data sources.
    \item \texttt{reconstructed.<stream\_id>} — a temporally complete stream that merges original observations with synthetically generated events introduced to fill missing data points, ensuring continuity across the timeline.
\end{itemize}


The \texttt{observed} topic thus holds only authentic readings, while the \texttt{reconstructed} namespace maintains a temporally complete, uncertainty-aware event stream.
Because both follow a common event schema, modules can seamlessly switch between observed-only or fused data depending on their operational needs.

\paragraph{Prefix-Based Filtering and Routing.}
ZMQ’s built-in prefix-matching subscription enables efficient filtering and dynamic routing of messages.
Modules may subscribe to topic prefixes (e.g., \texttt{observed.*}) to receive all observed streams without enumerating each explicitly.
This mechanism reduces message duplication and allows flexible composition of event flows, making it particularly suited for dynamically evolving SoS environments where streams may appear or disappear at runtime.

\paragraph{Endpoints, Roles, and Visibility.}
The system follows a distributed client–server topology in which all participants share the same set of messaging endpoints, collectively forming the event bridge.
Each module—whether publisher or subscriber—connects to this bridge, ensuring a consistent global view of the SoS data stream.
Within this architecture, modules formally declare themselves as event generators (e.g., data sources or reconstructors) or event consumers (e.g., CEP engines, loggers, or controllers).
By maintaining the same endpoints, all participants operate within a synchronized event plane, meaning that any message broadcast by one constituent becomes immediately visible to all subscribers authorized for that topic.
This design ensures transparency, reproducibility, and system-level situational awareness while preserving constituent autonomy: each DT determines which streams it publishes and consumes.

\paragraph{Extensibility and Modularity.}
Because all topics adhere to a unified schema, new DTs or analytical components can attach to the event plane dynamically without reconfiguration.
This plug-and-play design allows the SoTS to evolve organically as new data sources, filters, or event-processing rules are introduced, sustaining interoperability and composability across the framework.

\begin{figure}[H]

\caption{Flow of an event through the system}

The sequence diagram (Figure~\ref{fig:architecture_system_flow}) illustrates the interaction between the major components of the framework.
The process occurs in three phases: \textbf{Event Generation}, \textbf{Reconstruction}, and \textbf{Complex Event Processing}.

\subsubsection*{(1) Event Generation}
The \textit{Researcher} initiates data collection through the \textit{Stream} component.
The \textit{Coordinator} periodically invokes the \texttt{generate\_event()} routine, converting sensor readings into standardized event objects.
Each event is published to the \textit{EventStream} under the \texttt{"observed"} topic, carrying the most recent real sensor values.

\subsubsection*{(2) Reconstruction}
The \textit{Reconstructor} continuously consumes events from the \texttt{"observed"} stream, using the real values to update the internal state of its predictors.
Each event is then augmented with metadata derived from the predictors, such as confidence and the predicted value, and republished into the \texttt{"reconstructed"} stream.
If a temporal gap is detected, the \textit{Coordinator} directly invokes the \textit{Reconstructor}, which synthesizes a missing event using the active predictor (e.g., Kalman filter). The resulting synthetic event is inserted into the reconstructed stream, ensuring that all timestamps are represented and no temporal gaps remain.

\subsubsection*{(3) Complex Event Processing}
The \textit{CEP Engine} subscribes to the \texttt{"reconstructed"} stream and applies pattern-matching rules to detect higher-level phenomena such as anomalies or behavioural trends. 
Each event carries confidence metadata that quantify the estimated reliability of its reconstructed values. 
These attributes are retained throughout the CEP evaluation process, enabling rules to compute, aggregate, and query confidence levels across correlated events. 
The resulting complex events are then logged for downstream analysis.

\subsection{Implementation Details}
\label{sec:implementation_details}

The framework is implemented primarily in \textbf{Python~3.10}, with a complementary \textbf{Java~21} component providing access to the Esper CEP Engine. 
The two environments communicate through \textbf{ZeroMQ} sockets using JSON-encoded event messages. 
Configuration files written in JSON define stream parameters, reconstruction models, and CEP patterns, allowing experiments to be modified or reproduced without altering the source code.

\paragraph{Runtime Integration.}
The Java process is launched automatically by the Python runtime when the CEP module is enabled, establishing an inter-process bridge between the two environments. 
Esper runs as an independent Java process, while stream generation, coordination, and reconstruction are handled entirely in Python. 
Events are serialized as JSON objects and exchanged through ZeroMQ sockets, providing a lightweight, transport-agnostic channel for cross-language communication. 

\paragraph{Dependencies.}
\textbf{Python:} NumPy, SciPy, Pandas, PyZMQ, scikit-learn, pytest.  
\textbf{Java:} Esper~9.0.0, Gson, Jackson Databind, JeroMQ, Janino, Commons-Compiler, SLF4J.

\paragraph{CEP Integration.}
During execution, the Python \textit{Reconstructor} publishes reconstructed events to a ZeroMQ topic subscribed to by the Java CEP engine. 
Incoming JSON-formatted messages are parsed and injected into the Esper runtime, where they are continuously evaluated against event-pattern rules defined in external configuration files. 
When a rule condition is satisfied, Esper emits a pattern match—annotated with aggregated confidence levels, which is logged for further analysis.

\section{Scope and Limitations}
\label{sec:architecture_scope}
The architecture currently assumes in-order event delivery. 
Late or out-of-order events are not reprocessed by the CEP engine, as this would require event-time semantics and rule retraction capabilities beyond the current scope. 
However, delayed readings may be used in future work for batch updates of predictive models, when late data arrives.

\section{Summary}
\label{sec:architecture_summary}
This chapter outlined the design and operation of the uncertainty-aware SoTS framework. 
It introduced the Reconstruction, Coordinator, and CEP layers, each implementing a core aspect of uncertainty management. 
The messaging model enables modular integration of independent constituents, supporting the SoTS principles of autonomy and composability. 
Together, these components realize a system capable of maintaining data continuity and transparent confidence propagation across heterogeneous event streams.
