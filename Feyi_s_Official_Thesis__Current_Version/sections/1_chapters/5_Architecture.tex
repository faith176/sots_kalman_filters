\chapter{Architecture}\label{ch:architecture}

The architecture of the proposed framework is designed to enable reliable event processing and reasoning within SoTS. Building on the uncertainty challenges discussed in \chref{ch:background} and the reliability gaps identified in \chref{ch:literature-review}, this chapter develops the conceptual foundations, architectural requirements, system design, and implementation of the proposed solution.


\section{Description of the Approach} \label{sec:approach}
The proposed architecture introduces a method for enabling event-driven systems, particularly those embedded within SoTS, to continue operating when expected observations temporarily fail to arrive. The core idea is to treat short-term data gaps as explicit, detectable conditions within the event pipeline and to provide a structured method for generating substitute observations whose quality is known. At a high level, the approach augments a standard event-driven pipeline with a reconstruction stage placed between the data source and the reasoning engine. This stage tracks the expected arrival schedule of each stream, detects when an observation fails to appear on time, and invokes a predictive model maintained by the digital twin to estimate what the missing observation would have been. The reconstructed event is emitted in the same structure as a normal observation but includes an additional confidence value reflecting the predictive model’s uncertainty. Both reconstructed and genuine events are forwarded to the CEP engine without requiring any changes to CEP queries or operators. The CEP engine processes the combined stream as usual, with the option to interpret confidence information when relevant.

Figure~\ref{fig:uml} presents a conceptual view of the architecture. The system is organized into three layers, the Messaging Layer, Processing Layer, and Data Layer, which together form a pipeline for detecting missing observations, reconstructing substitutes, and forwarding uncertainty-annotated events to the CEP engine. Each layer has a specific set of responsibilities, enabling modularity and clear separation of concerns.

The architecture operates as follows. Event generators publish observed data into the system through the Messaging Layer. The Processing Layer monitors expected arrival schedules, detects missing observations, and invokes predictive models to reconstruct substitutes when necessary. Both observed and reconstructed events flow to the CEP engine, which evaluates event patterns without requiring modifications to query semantics. The Data Layer provides unified event representations that standardize how timestamps, payloads, and confidence metadata are managed across the system.

\subsection{Messaging Layer}

The Messaging Layer defines the communication interfaces used for sending and receiving events. Its purpose is to abstract away protocol-specific details so that higher-level logic remains independent of communication technology.

\paragraph*{EventGenerator and EventConsumer}
These interfaces define generic contracts for publishing and subscribing to event streams. They enable heterogeneous sensors, data sources, and DT components to be treated uniformly.

\paragraph*{EventStream}
Represents a logical communication channel over which both observed and reconstructed events are exchanged. It maintains temporal ordering and encapsulates stream identifiers and metadata.

\paragraph*{Client and Server}
These classes abstract the underlying communication mechanism (e.g., ZeroMQ or MQTT). By encapsulating publishing and subscription behaviour, they allow the architecture to remain independent of transport protocols.

\subsection{Processing Layer}

The Processing Layer contains the operational logic responsible for detecting gaps, reconstructing missing events, and delivering enriched streams to CEP.

\paragraph*{Coordinator}
The central orchestrator of the processing workflow. It monitors incoming streams, manages timing expectations, and uses the \textit{StreamScheduler} to determine when an observation is overdue.

\paragraph*{StreamScheduler}
Tracks the expected arrival times for each stream and signals the Coordinator when a missing observation should be reconstructed.

\paragraph*{Reconstructor}
Consumes observed events, determines when reconstruction is necessary, and generates substitute events. It invokes a \textit{Predictor} to estimate missing values and attaches quantitative confidence metadata to each reconstructed event.

\paragraph*{Predictor}
An abstract interface for digital-twin forecasting models. Implementations may use filtering, machine learning, simulation, or other techniques, but the Reconstructor treats them uniformly.

\paragraph*{CEPEngine}
Evaluates event patterns over the combined stream of observed and reconstructed events. Confidence values are made available as attributes, allowing CEP queries to incorporate uncertainty if desired.

\subsection{Data Layer}

The Data Layer provides the shared data structures used across the architecture. These entities ensure consistent handling and annotation of event information.

\paragraph*{Stream}
Represents a logical data source, including identifiers, data types, and expected sampling intervals. It provides the context needed for gap detection.

\paragraph*{Event}
The base representation for all messages in the system. Contains timestamps, payload data, and metadata associated with the original observation.

\paragraph*{ReconstructedEvent}
Extends \textit{Event} to include predicted values, confidence levels, and reconstruction method identifiers. This structure ensures that downstream components can distinguish genuine from reconstructed observations while maintaining a consistent event format.

Figure~\ref{fig:process-flow} shows the end-to-end runtime behaviour of the system. It illustrates how observed and reconstructed events move through the architecture and how components interact under normal operation and during temporary data gaps.

\paragraph{Normal Event Flow}
When a generator produces an observation, the \textit{Stream} forwards it to the \textit{Coordinator}, which verifies that it arrived within its expected window. The event is then dispatched to the \textit{EventStream} and delivered to both the \textit{Reconstructor} and the \textit{CEP Engine}. In this path, the event is simply treated as an \emph{observed} input.

\paragraph{Gap Detection and Reconstruction}
If an expected event fails to appear on time, the \textit{Coordinator} detects the gap and issues a \texttt{triggerReconstruction()} request. The \textit{Reconstructor} then invokes the digital twin’s \textit{Predictor} to estimate the missing value and compute a corresponding confidence score. The resulting \textit{ReconstructedEvent} is structurally identical to an observed event but annotated with confidence metadata, and is then published back into the EventStream.

\paragraph{CEP Processing}
The \textit{CEP Engine} consumes both observed and reconstructed events without requiring changes to query logic. Confidence is available as an attribute for pattern evaluation but does not alter the semantics of existing operators.


\section{Implementation}\label{sec:implementation}
Python~3.10 is used for the reconstruction layer. It provides extensive libraries for numerical computation and state-estimation methods, and its flexibility supports rapid prototyping of predictive components.

The CEP engine is implemented in Java~21 using the Esper library. The project is built with Maven (version~3.6), which compiles and packages the engine into a self-contained executable JAR. Esper provides an efficient runtime for evaluating continuous event queries, enabling low-latency processing of both observed and reconstructed events.

To connect the Python-based reconstruction layer with the Java-based CEP engine, the system uses lightweight message passing through ZeroMQ~\cite{zeromq_org}. This design keeps the components decoupled, allowing each subsystem to evolve, be replaced, or be scaled independently without modifying the other.


\subsection{Libraries and Tools}
Several libraries support the implementation:

\begin{itemize}
    \item \textbf{NumPy} and \textbf{pandas} for numerical computation and time-indexed event manipulation.
    \item \textbf{SciPy} for interpolation and auxiliary statistical routines.
    \item \textbf{FilterPy} for implementing the Kalman filter used by the predictor.
    \item \textbf{matplotlib} for evaluation plot visualizations.
    \item \textbf{pytest} for automated testing.
    \item \textbf{Esper} (Java) serves as the CEP engine, executing continuous queries and time-windowed pattern detection without modification to its query model.
    \item \textbf{ZeroMQ (pyzmq)} provides asynchronous publish–subscribe communication between components
\end{itemize}

The system is modular: predictors, communication mechanisms, and CEP engines can be replaced without altering the architecture, allowing the framework to be adapted to different SoTS environments and technology stacks.
