\chapter{Demonstration}\label{ch:demonstration}
This chapter demonstrates the utility of the proposed approach through a case study of a CEP system operating over a SoTS. CEP is a technique for analyzing streams of events from distributed sources to identify patterns and system conditions over time~\cite{flouris2017issues}. It has well-established model-driven foundations \cite{david2018foundations} and provides a suitable setting for evaluation, as it relies on continuous inputs from multiple constituents. The demonstration shows how the proposed statechart model integrates with a CEP pipeline to control how constituent measurements are utilized under varying lifecycle states, improving system reliability.\footnote{Implementation available at: \url{https://github.com/ssm-lab/sots_cep}}

First, I present the system architecture (\secref{sec:architecture}) and implementation (\secref{sec:implementation}); followed by the demonstration setup (\secref{sec:evaluation-setup}); the enactment of the case (\secref{sec:execution}); and the results (\secref{sec:results}).

\section{System Architecture}\label{sec:architecture}
This section shows how the proposed approach implements the model described in \secref{sec:statecharts-reliability} within a middleware that supports CEP for SoTS. Within this architecture, the statechart model controls how constituents contribute events based on their lifecycle state. The system produces events only when the constituent's condition permits. The CEP engine operates downstream, consuming these events for complex event detection. At level~4 (\secref{sec:lv4}), the model introduces a restricted role that constituents can enter under degraded conditions. In this architecture, this role is supported through a compensation component that reconstructs missing events.


\subsection{Component Model of Architecture}\label{sec:architecture-component-model}

\centering

\caption{Component model}
\label{fig:component-model}

\figref{fig:component-model} shows the component model of the architecture. It illustrates how statechart models are integrated to control event production, processing, and compensation. \textit{Event Sources} read measurements from constituents and convert them into events. Before emitting an event, they consult the \textit{Lifecycle Manager}, which determines whether the event should be produced or suppressed based on the constituent's current state. Events are then sent to the \textit{Event Stream}, which distributes them to downstream components. The \textit{Event Processor} consumes these streams to perform CEP. When a constituent cannot provide complete or valid inputs, it may remain active in a restricted role. In these cases, the \textit{Event Compensator} ensures that the \textit{Event Processor} continues to receive usable inputs. It uses a \textit{Predictor} to estimate measurements and a \textit{Reconstructor} to generate replacement events for inconsistent data.


\section{Implementation}\label{sec:implementation}
\begin{figure}[htp]
\centering
\includegraphics[width=0.9\textwidth]{figures/Architecture/UML Model.drawio.png}
\caption{Class diagram}
\label{fig:uml-model}
\end{figure}
\figref{fig:uml-model} shows the system implementation. Components are deployed as services connected through a ZeroMQ-based \textit{Event Stream}. \textit{Event Sources} generate structured JSON events from constituent observations, including values, timestamps, and metadata such as confidence. These events are published to the event stream and routed using topic-based filtering. Python services control lifecycle state and event generation through a \textit{Lifecycle Manager} implemented with Itemis CREATE statecharts. The \textit{Event Compensator} monitors the stream and reconstructs missing events when needed using a Kalman filter \textit{Predictor}. A Java-based \textit{Event Processor} built with Esper consumes these event streams and evaluates patterns to detect system-level behaviour.

In this implementation, the proposed model is realized as lifecycle statecharts that control each constituent. These statecharts track belonging and health and determine when events are produced or reconstructed. Itemis CREATE generates executable code from the statechart models. \figref{fig:itemis-diagram} shows the model implemented with Itemis CREATE\footnote{See: \url{https://www.itemis.com/en/products/itemis-create}.}. The \textit{Lifecycle Manager} component (\secref{sec:architecture-component-model}) maintains an instance of the lifecycle statechart for each constituent and exposes its current state. Other components subscribe to state changes to detect relevant transitions. Through these state changes, the lifecycle model enables or disables event production and compensation, directly controlling system behaviour.

Lifecycle state determines when constituents can participate and contribute. System components consult the Lifecycle Manager to decide when event production, updates, and reconstruction are allowed. \tabref{tab:state-behaviour} summarizes the behaviour associated with each state. Constituents contribute to the SoTS only when they are in \textit{Participating} states. In \textit{Prepared} and \textit{Disengaged}, they are not part of the SoTS and do not emit events. The Compensator component updates its predictor in all \textit{Active} and \textit{Passive} states so it remains calibrated when the constituent is able to contribute.


\subsection{Compensation under Restricted Roles}\label{sec:demo-compensation}
The \textit{Restricted Role} allows degraded constituents to continue contributing while limiting their influence on system behaviour. In this role, missing observations are reconstructed by the \textit{Event Compensator} (\secref{sec:architecture-component-model}), allowing the constituent to continue supplying inputs to the CEP engine. Each reconstructed event is assigned a confidence value. As long as confidence remains above a threshold, the constituent continues in a restricted role; otherwise, it is withdrawn to prevent poor-quality contributions. Compensation is implemented using a Kalman filter to estimate missing measurements (see \secref{sec:kalman-formulation}). Confidence is computed using the normalized innovation squared (NIS), a measure of prediction consistency (see \secref{sec:predictor-confidence}), and decays as the filter's uncertainty increases.

\section{Demonstration Setup}\label{sec:evaluation-setup}
This section describes the setup used to demonstrate how the proposed approach supports reliable behaviour in a CEP-based SoTS under data loss. I use a controlled simulation with three constituents generating continuous data streams. Health states are manually progressed over time to create a controlled degradation and recovery scenario, introducing data loss at different stages. All constituents follow the same health progression. The setup focuses on missing observations only, assuming that the CEP engine expects inputs at regular intervals; when expected data is not received, compensation is triggered.

This allows us to observe how the approach uses lifecycle statecharts to control when and how each constituent contributes to the event stream, which is then processed by the CEP engine to detect complex events. The demonstration is conducted in a simulated setting and does not capture the full complexity of large-scale SoTS deployments. It focuses on disturbances caused by missing observations, with compensation limited to reconstructing missing events.

\subsection{Parameters}
The experiment runs for 500 time steps. Three constituents generate time series initialized around 50, with drift parameters of $0.05$, $0.02$, and $-0.03$, and noise levels of $0.02$, $0.03$, and $0.03$. Health evolves from \textit{Ideal} ($t=0$) to \textit{Erroneous} ($t=100$), \textit{Malfunctioning} ($t=200$), \textit{Degraded} ($t=375$), and \textit{Failed} ($t=400$), before recovering to \textit{Ideal} ($t=440$). As health worsens, event drop probabilities increase (0\%, 45\%, 55\%, 60\%, and 100\%), leading to more frequent and longer gaps in observations. Missing observations are reconstructed using a Kalman filter with $Q = 0.01$, $R = 0.25$, and $\Delta t = 1$, modelling value and rate of change as a two-dimensional state. 

The evaluation considers three CEP patterns applied to the data streams received by the CEP engine: \textit{Agreement}, where streams exhibit similar values; \textit{Divergence}, where streams differ significantly; and \textit{Stability}, where streams move in the same direction over time. Full Esper pattern language (EPL) specifications are provided in \secref{app:patterns}.

\section{Results}\label{sec:results}
This section evaluates how the proposed approach maintains reliable behaviour under disturbances caused by missing observations. Reliability is assessed in terms of the system’s ability to continue operating and support accurate complex event detection despite data loss. To evaluate this, I consider two aspects: (i) the accuracy of reconstructed data using mean absolute error (MAE) and root mean squared error (RMSE), and (ii) the performance of the CEP layer using precision, recall, F1, and F2 scores.


\input{tables/Results/compensation_results.tex}
\tabref{tab:disturbance-metrics} shows that missing observations occur frequently across all constituents, with data availability between 0.65 and 0.68. These appear as short gaps in the data. Despite this, reconstruction remains accurate, with low MAE and RMSE, indicating that the filter is able to accurately estimate missing measurements.


\tabref{tab:pattern-results} compares the CEP layer’s complex event detection performance with and without compensation. Recall improves across all event patterns when compensation is enabled. The largest gains are observed for divergence (0.366 to 0.593) and stability (0.481 to 0.688), with the agreement pattern also improving (0.820 to 0.874). Precision decreases slightly due to uncertainty introduced during reconstruction, especially over longer gaps, but remains high overall. As a result, both F1 and F2 scores improve.
\input{tables/Results/cep_results.tex}

Overall, these results demonstrate how the proposed approach manages disturbances by controlling when and how constituents contribute to the system, and compensating as needed. By coupling system components to lifecycle statecharts, behaviour is enforced automatically: contributions are enabled or halted based on state, and reconstruction is triggered in restricted roles. This shifts disturbance handling to the system level, where the model manages how constituents interact with the event stream. As a result, the approach maintains continuous event streams for CEP, while compensation improves pattern detection compared to uncompensated execution.
