\chapter{Demonstration of Utility}\label{ch:demonstration}
This chapter demonstrates the practical utility of the reliability model introduced in \chref{ch:reliable-sots} through the implementation of a DT service that supports CEP in SoTS. The service integrates lifecycle statechart models to control how DTs contribute to the event stream based on their operational condition. It operates as a control layer over these streams, ensuring that only valid events are supplied to the downstream CEP engine.

The chapter first presents the system architecture used to realize the model (\secref{sec:architecture}). It then describes the implementation of the CEP-based middleware (\secref{sec:implementation}) and explains how lifecycle statecharts enforce participation constraints, including compensation under restricted roles (\secref{sec:statechart-behaviour}). Finally, it introduces the experimental setup used to evaluate the impact of lifecycle control and compensation on system reliability (\secref{sec:evaluation}).



\section{System Architecture}\label{sec:architecture}
The Level~4 adaptive reliability model (see \secref{sec:lv4}) defines how constituent contributions are controlled under varying system conditions. In the demonstrated architecture, this model is realized within a DT service layer, where state controls how DTs generate and contribute events. CEP operates as a downstream consumer of these event streams. Realizing this model requires support for the followin , First, contributions to the event stream are controlled based on lifecycle state, ensuring that constituents only provide input when their condition permits it. Second, the system supports continued operation under degradation by compensating for missing or faulty data, allowing constituents to remain active in restricted roles. Third, compensated contributions are bounded by uncertainty to prevent unreliable inputs from affecting system behaviour. Finally, event production is separated from system-level processing, so that the CEP engine operates only on validated or compensated inputs.

\textit{Event Sources} take measurements from components and convert them into events. The \textit{Event Stream} distributes these events, and the \textit{Event Processor} consumes them to perform CEP. The model allows constituents to remain active in the SoTS in a restricted role during periods of degradation. To support this, the \textit{Event Compensator} ensures that the \textit{Event Processor} continues to receive usable inputs during instability. It uses the \textit{Predictor} to estimate values when needed, and the \textit{Reconstructor} generates replacement events to compensate for missing or faulty data.



\section{System Implementation}\label{sec:implementation}
The architecture is implemented as an event-driven middleware with Python-based coordination services and a Java-based CEP engine. The Python layer manages lifecycle state and event generation through a \textit{Lifecycle Manager} implemented using Itemis CREATE statecharts. Events are transmitted via a ZeroMQ-based \textit{Event Stream} and processed by an \textit{Event Processor} built with the Esper CEP engine. An \textit{Event Compensator} monitors the stream and reconstructs events when needed using a Kalman filter-based \textit{Predictor}.

\subsection{Enforcing the SoTS Reliability Model with Executable Statecharts}\label{sec:statechart-behaviour}
The reliability model introduced in \secref{sec:reliability-levels} defines lifecycle constraints that govern how constituents participate and contribute in a SoTS. In this implementation, these constraints are enforced through executable lifecycle statecharts associated with each constituent. These statecharts maintain belonging and health states and directly control runtime behaviour, determining when events can be produced, modified, or reconstructed.

\subsubsection{Statechart-Controlled Runtime Behaviour}
The system enforces the Level~4 adaptive reliability model (\secref{sec:lv4}) by using lifecycle state to control participation and contribution. System components consult the lifecycle controller to determine when event production, updates, and reconstruction are permitted. \tabref{tab:state-behaviour} summarizes the behaviours associated with each state.

Constituents contribute to the SoTS by supplying events to the CEP pipeline only when they are in participating \textit{Active} states. In \textit{Prepared} and \textit{Disengaged} states, constituents are not part of the SoTS and do not contribute events, and their measurements are not maintained by the system. Within the \textit{Active} states, only \textit{Full Role} and \textit{Restricted Role} contribute events forS CEP processing, while \textit{Pending Entry} and \textit{Pending Exit} do not. In both \textit{Active} and \textit{Passive} states, the compensator updates its internal predictor to ensure it remains calibrated before entering or returning to the \textit{Active} state.


\subsection{Compensation under Restricted Roles}\label{sec:demo-compensation}
The \textit{Restricted Role} introduced in Level~4 allows degraded constituents to continue participating while limiting their influence on system-level behaviour. In this role, missing or unreliable observations are compensated through reconstruction, enabling continued contribution to the CEP pipeline under constrained conditions. Reconstructed events are associated with a confidence measure that determines whether participation can continue: as long as confidence remains above a threshold, the constituent operates in a restricted capacity; otherwise, the lifecycle statecharts enforce withdrawal to prevent unreliable contributions. In the CEP-based SoTS, compensation is implemented as an estimation process that reconstructs missing events based on an internal model of system behaviour \cite{hanmer2013patterns}. This is realized using Kalman filters \cite{kalman1960filtering} (see Appendix~\secref{sec:kalman-formulation}), implemented in Python using the FilterPy library\footnote{FilterPy is a Python library for Kalman filtering and Bayesian estimation. \url{https://filterpy.readthedocs.io}}.

In the CEP architecture, it is necessary to quantify how well the predictor estimates the underlying data. In Kalman filtering, uncertainty increases during prediction, reflected by the growth of the state covariance, which leads to increasing uncertainty in reconstructed events. When observations are available, the consistency of predictions can be evaluated using the normalized innovation squared (NIS). The NIS measures the agreement between predictions and observations by scaling the prediction error by its expected uncertainty \cite{bar2001estimation,simon2006optimal} (see Appendix~\secref{sec:kalman-formulation}). A low NIS indicates that the prediction error is small relative to its uncertainty, implying good consistency with observed data, while a high NIS indicates a larger than expected deviation.

Based on this, a confidence measure is defined to capture both prediction consistency and uncertainty growth:
\begin{equation}
c =
\begin{cases}
\frac{1}{1 + \mathrm{NIS}}, & \text{if a measurement is available} \\
c_{\text{prev}} \cdot e^{-P}, & \text{otherwise}
\end{cases}
\end{equation}
where $P$ denotes the state covariance.

When measurements are available, confidence is computed from the NIS, assigning higher confidence to predictions that closely match observations. When measurements are unavailable, confidence decays exponentially as the state covariance grows, reflecting increasing uncertainty during prediction-only periods. This confidence value is used by the lifecycle statecharts to determine whether a constituent remains in the \textit{Restricted Role} or must withdraw.


\subsection{Supporting Event Processing Infrastructure}
To enable lifecycle-driven control of constituent contributions, observations are processed through an event-driven pipeline. Observations generated by constituents are converted into structured JSON events and published to an event stream. Event transport is handled by ZeroMQ (ZMQ)\footnote{ZeroMQ is a high-performance messaging library supporting publish--subscribe communication. \url{https://zeromq.org}}, which provides a lightweight publish--subscribe layer between the Python middleware and the Java-based CEP engine. A ZMQ broker routes events between publishers and subscribers, using topic-based filtering to distinguish observed and reconstructed events.

\input{tables/Implementation/topic_filtering.tex}

System-level behaviour is detected from the event stream using the Esper CEP engine\footnote{Esper is a complex event processing engine for analysing event streams. \url{https://www.espertech.com/esper}}. The engine evaluates event patterns written in the Event Processing Language (EPL), where simple patterns operate on individual events and more complex patterns combine them to detect higher-level behaviours.



\section{Evaluation}\label{sec:evaluation}
This section evaluates the proposed SoTS statechart model through a proof-of-concept implementation. The evaluation focuses on a CEP-based SoTS, where multiple constituents generate data streams that are sent to a CEP engine to detect complex events at the system level. In this setting, disturbances such as missing observations affect the quality and completeness of the event stream, influencing the accuracy of detected system-level patterns. A controlled simulation is used to evaluate the system under disturbance. Three simulated constituents generate continuous data streams, forming a simple SoTS. Disturbances are introduced through health degradation, which causes intermittent data loss. As the system moves through stable operation, degradation, and recovery, lifecycle statecharts act as the SoTS coordination layer, controlling whether and how each constituent contributes to the event stream. By restricting participation based on constituent condition, the system reduces the impact of unreliable or missing data on the event stream used for CEP processing. 

\paragraph{Limitations of the Demonstration}
The system is evaluated in a controlled setting and does not capture the full complexity of large-scale SoTS deployments. The evaluation focuses on disturbances caused by missing observations, with compensation limited to reconstructing absent events.

\subsection{Demonstration Parameters}
The experiment runs for 500 time steps. Three constituents generate time series initialized around 50, with drift parameters of $0.05$, $0.02$, and $-0.03$, and noise levels of $0.02$, $0.03$, and $0.03$. The health of each constituent evolves over time from \textit{Ideal} ($t=0$) to \textit{Erroneous} ($t=100$), \textit{Malfunctioning} ($t=200$), \textit{Degraded} ($t=375$), and \textit{Failed} ($t=400$), before recovering to \textit{Ideal} ($t=440$). As health degrades, event drop probabilities increase (0\%, 45\%, 55\%, 60\%, and 100\%), leading to progressively more frequent and longer sequences of missing observations. Missing observations are compensated using a Kalman filter with $Q = 0.01$, $R = 0.25$, and $\Delta t = 1$, modelling value and rate of change as a two-dimensional state. \tabref{tab:patterns} summarizes the evaluated complex event patterns, while full Esper EPL specifications are provided in Appendix~\ref{app:patterns}.

\subsubsection{Compensation Performance}
\input{tables/Results/compensation_results.tex}

As shown in \tabref{tab:disturbance-metrics}, missing observations occur frequently across all constituents, with data availability ranging from approximately 0.65 to 0.68. These appear as short sequences of consecutive missing values. Despite this, reconstruction remains accurate, with low MAE and RMSE relative to the scale of the time series. This indicates that the compensation mechanism is able to approximate the underlying behaviour while filling gaps in the observed data.

\input{tables/Results/cep_results.tex}
\tabref{tab:pattern-results} shows that recall improves across all complex event patterns when compensation is enabled, reflecting the system's ability to detect behaviours that would otherwise be missed due to missing observations. The largest gains are observed for divergence (0.366 to 0.593) and stability (0.481 to 0.688) patterns, with the agreement pattern also improving (0.820 to 0.874). These improvements come with a slight reduction in precision, as reconstruction introduces uncertainty, particularly during longer gaps where predictions are less reliable. Despite this, precision remains high overall, resulting in improved F1 and F2 scores.

This evaluation demonstrates that enforcing participation constraints at the SoTS level, together with compensation for missing data, improves the reliability of system-level event detection under disturbance.
